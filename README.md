# CRYPTO INVESTOR — Telegram Mini App (backend v2)

Это рабочая основа Telegram Mini App: существующий игровой интерфейс подключён к серверному API, а состояние игрока хранится в PostgreSQL. Баланс и покупки больше не доверяются браузеру.

## Что реализовано

- Проверка подлинности `Telegram.WebApp.initData` на сервере по официальному алгоритму Telegram.
- Серверная игровая сессия, привязанная к Telegram ID.
- Серверный баланс, счётчик тапов: +50 ₽ за каждое нажатие, плюс бонус +500 ₽ за каждое 100-е нажатие.
- Покупка апгрейдов, активов и улучшение активов — внутри транзакций PostgreSQL с блокировкой строки игрока.
- Пассивный доход, включая офлайн-период (максимум 8 часов за одно начисление).
- PostgreSQL для постоянных данных, Redis для общего rate limit между репликами.
- Docker Compose для локального запуска, health endpoint и пример конфигурации Nginx.

Платежи, вывод денег, блокчейн и реальные криптоактивы НЕ подключены. Валюта в игре — только виртуальные рубли (₽); других валют нет.

## Локальный запуск

Требуется Docker и Docker Compose.

1. Установите Node.js 20+ и Docker с Docker Compose.
2. В каталоге проекта выполните `npm run secrets:generate`. Команда создаст `.env` с уникальными случайными `SESSION_SECRET` и `POSTGRES_PASSWORD` и ограничит доступ к файлу правами владельца. Существующий `.env` команда не перезаписывает.
3. Откройте `.env` и вставьте реальный токен бота от [@BotFather](https://t.me/BotFather) вместо `PASTE_REAL_TOKEN_FROM_BOTFATHER_HERE`. Никогда не вставляйте токен в `script.js` или другие публичные файлы.
4. Запустите: `docker compose up --build -d`.
5. Проверьте: `curl http://localhost:3000/health`.

Для локальной проверки через Telegram нужен публичный HTTPS URL. Разместите приложение за HTTPS reverse proxy / tunnel и настройте домен Mini App у BotFather. В BotFather используйте `/setmenubutton`, выберите бота, задайте текст кнопки (например, «Играть») и HTTPS URL приложения. В настройках Mini App задайте тот же домен. Открывайте игру именно из Telegram: прямой запуск в обычном браузере намеренно не авторизует игрока.

## API

- `POST /api/auth/telegram` — проверка `initData`, выдача сессии.
- `GET /api/game/state` — состояние игрока.
- `POST /api/game/tap` — одно нажатие.
- `POST /api/game/buy-upgrade` — `{ "upgradeId": "tap2" }`.
- `POST /api/game/buy-asset` — `{ "assetId": "car1" }`.
- `POST /api/game/upgrade-asset` — `{ "assetId": "car1" }`.
- `GET /api/leaderboard` — топ-20 игроков.
- `GET /health` — проверка процесса и БД.

## Масштабирование

**200 000 одновременных пользователей не гарантируются одним Docker-хостом или этим стартовым compose-файлом.** Это целевой показатель, который нужно подтвердить нагрузочными испытаниями и обеспечить соответствующей инфраструктурой.

Перед публичным запуском на большой аудитории:

1. Развернуть несколько stateless API-реплик за managed load balancer / Nginx ingress. В `ops/nginx.conf.example` приведён шаблон.
2. Включить TLS, WAF/DDoS-защиту и ограничение запросов на edge-уровне. Redis rate limit уже общий для реплик приложения.
3. Использовать managed PostgreSQL с multi-AZ, автоматическими бэкапами, мониторингом и пулером соединений (например, PgBouncer). Рассчитать общий размер пулов: `число реплик × PG_POOL_MAX` не должно превышать лимит БД.
4. Redis перевести в managed HA-конфигурацию; контролировать память, latency и hit rate.
5. Добавить метрики (RPS, p50/p95/p99, ошибки, DB pool wait, блокировки, Redis latency), централизованные логи и алерты.
6. Провести нагрузочные тесты ступенями (например, 1k → 10k → 50k → 100k → 200k виртуальных пользователей), включая всплески входа, тапов и покупок. Уточнить профиль активности: 200k открытых Mini App и 200k активных запросов/сек — принципиально разные нагрузки.
7. Для больших потоков тапов перейти на пакетную запись/очередь событий с идемпотентностью и отдельной обработкой экономики; текущая реализация делает транзакционную запись на каждый тап и является корректной стартовой версией, но не доказанно выдерживает целевой пик.

Не публикуйте `.env`, не добавляйте его в Git, не отправляйте в мессенджерах и не вставляйте секреты в скриншоты. Если `.env` или токен бота утёк, немедленно смените токен через @BotFather и пересоздайте секреты с плановой ротацией сессий. Не запускайте несколько копий текущего `docker-compose` как production-кластер без внешних PostgreSQL/Redis, балансировщика, секрет-менеджмента и расчёта пула соединений.
